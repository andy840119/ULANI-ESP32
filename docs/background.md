# 這個專案的由來與決策

`protocol.md` 記的是協定「長什麼樣」，這份記的是「為什麼會有這個專案」和「為什麼這樣
選型」——那些從程式碼看不出來、但會影響未來判斷的前因後果。

## 這台日曆原本怎麼更新

ULANI 電子日曆原本靠**官方手機 App**：App 留在背景，手機靠近日曆時就在背景把圖算好、
透過藍牙送過去。實際用起來有兩個問題：**有時候就是不會更新**（原因沒確認過——可能是
藍牙連線，也可能是手機把 App 從背景清掉了），而且**官方已經不再維護這個 App**。

要誠實標記：「不會更新」的成因是**推測，不是結論**，本專案沒對官方 App 做過任何量測。
記下來是因為它是這個專案的動機，不是因為它被證實。

## 中間的一站：PC 上的藍牙 driver

後來有人寫了跑在電腦上的藍牙 driver，逆向出日曆的協定，讓「電腦在旁邊時」也能更新：
[Grassboy/ULANI.node.js](https://github.com/Grassboy/ULANI.node.js)。**本專案的協定層
完全來自這份逆向工程成果**，包括那些刻意保留的怪癖（見 `protocol.md`）。

不過它解決的仍是同一類問題：需要**一台開著、而且在旁邊的通用電腦**。

## 為什麼是 ESP32

手機和電腦都有同一個毛病：**它們是通用裝置，不保證在場、也不保證醒著。** ESP32 的價值
在於它是一台**專職、常駐、不需要人在旁邊**的裝置——一直待在日曆附近、一直有電、不會被
系統把背景程序清掉。而且它同時內建**藍牙和 WiFi**：藍牙拿來連日曆，WiFi 拿來連家裡網路
去跟畫面來源拿圖，一片就夠，開發也單純。

## 為什麼是 Tesserae

有了常駐裝置，還缺「圖從哪來」。與其自己在韌體裡做排版、字型、天氣抓取，不如把這件事
交給專門做這件事的服務：[Tesserae](https://github.com/dmellok/tesserae) 是可自架的儀表板
服務，把每台裝置畫成一張 dashboard，樣式和更新頻率都在它的網頁上設定。

它剛好對得上這個專案要的形狀：**一台裝置一張畫面**（ULANI 四頁就接四個 client），而且
它算出來的位元組格式（`seeed_ee04_73e6`：800×480、4bpp packed）和 ULANI **完全相同**，
所以 **ESP32 不需要做任何影像處理**——server 算好，板子照抄送進日曆。唯一的轉換是調色盤
順序，用一張 16 格對照表在下載串流時換掉（見 `protocol.md`）。

更新走 REST 輪詢：板子 `POST /status`，server 在回應裡給 `next_poll_s`，板子照著等那麼久
再回來問。Tesserae 另有 MQTT/SSE 推送通道，但它自己把 SSE 定位成「最佳化，而非正確性
需求」，只給有觸控的面板做局部更新，所以這裡和官方 ESP32 韌體一樣走 REST 輪詢。

## 連線策略：不需要隨時連著

**一台日曆一次只能被一個裝置連著**（日曆本身的限制）。所以「ESP32 要不要一直連著日曆」
是個要選的問題。

本專案選**按需連線**：平常放掉藍牙連線，有事情要做時（收到新圖、切頁、或使用者打開後台）
自己連回去，做完閒置一段時間再放掉。這樣官方 App 也有機會連上，板子閒著時也比較不耗電、
不發熱——而且因為板子會自己連回來，放掉連線**不代表需要人在場**。閒置多久才放掉可以在
後台的「設定」裡調（`ULANI_IDLE_TIMEOUT_MS` 是預設值）。

一件無法再壓低的固定成本：日曆會把 op channel 靜默超過十秒的連線斷掉，所以**只要連著，
就得每十秒送一次 keepalive**。調「多久問一次狀態」省不到，因為那個封包本來就要送；真正的
旋鈕只有「要不要連著」和「閒置多久放掉」。

> 耗電**沒有實際量測過**，以上關於省電的說法都是推論。在有數字之前，不要把省電當成
> 決策的硬理由。
