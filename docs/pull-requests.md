# 發 PR 的規矩

**講重點。** PR 說明是給 reviewer 快速判斷「這改了什麼、為什麼、有沒有風險」，不是
把過程重講一遍。

## 內容

一個好的 PR 說明通常只要：

1. **一句話講改了什麼、為了什麼**（可附 issue 編號）。
2. **重點變動**——幾個 bullet，講「做了什麼決定」，不是逐行複述 diff。
3. **有沒有風險 / 要注意什麼**——相容性、要不要重新配對、要不要重刷、測了沒。

標題用一行祈使句，例如 `fix: modem-sleep the radio when idle (#23)`。

## 不要

- 不要長篇解釋不重要的細節，或把每個小改動都寫成一段。
- 不要把「我怎麼一步步查到的」寫進去；reviewer 要的是結論。
- 沒實際跑過就別寫「已驗證」。測了就說測了什麼、結果如何；跳過就說跳過。

## 例子

> **精簡**
> `feat: 韌體版本顯示在後台 (#37)`
> - release build 把 git tag 當版本號；本地 build 是 `dev`。
> - 新增 `GET /api/system/version`，後台頁尾顯示。
> - 實機確認：本地 build 顯示 `dev`，tag build 顯示版號。

> **囉嗦（別這樣）**
> 大段描述 CMake 怎麼讀 env、esp_app_desc 的欄位長度、每個檔案改了哪幾行、
> 一路試錯的過程……reviewer 看 diff 就好。
